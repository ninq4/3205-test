# Решение

## Что изменено

- Добавлена миграция `002_order_payments.sql`: фактическая оплата хранится в `amount_paid_kop` (целые копейки). Ограничение БД запрещает отрицательную оплату и оплату выше исходной суммы.
- Sync и вебхуки используют общую нормализацию и сохраняют `amountPaid`. Статистика возвращает `total`, `gross`, `discount`, `net`, включая нули для дней без оплат. `total = gross`, `discount = gross - net`. Учитываются только заказы в текущем статусе `paid`.
- Источник `net` — фактический `amountPaid`, а не пересчёт по проценту: платёжная система уже выполнила округление. `discountPercent` для этой задачи хранить не требуется.
- День заказа определяется в IANA-таймзоне клиента именно для `createdAt`. Текущее время сервера больше не участвует в расчёте.
- Исправлено преобразование рублей в копейки: `Math.floor(0.29 * 100)` давал 28 вместо 29. Масштабирование десятичного представления через `BigInt` сохраняет копейки и прежнее усечение настоящих долей копейки (`10.999 → 1099`). Небезопасные суммы и переполнение дневной суммы отклоняются.
- Проверка версии и запись заказа объединены в атомарный PostgreSQL upsert. Параллельные sync/вебхуки больше не могут перезаписать новую версию старой между SELECT и INSERT/UPDATE.
- Невозможная календарная дата вроде `2026-13-01` теперь даёт 400, а не ошибку `toISOString()` и 500.
- Добавлены Dockerfile, запуск приложения в Compose, проверки готовности и lockfile зависимостей. Миграции выполняются при старте, приложение работает от пользователя `node`.

Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.

## Причина расхождений по c_7

1. Запросил `GET http://localhost:4000/customers/c_7`: API вернул `Europe/Berlin`.
2. В исходном `TotalsService.daily()` обнаружил `tzOffsetMinutes(timezone, new Date())`: одно **текущее** смещение применялось ко всем историческим заказам.
3. 29 марта 2026 года в 01:00 UTC Берлин переходит с UTC+1 на UTC+2. Отчёт за 27–31 марта пересекает этот момент; даже внутри 29 марта нельзя использовать одно фиксированное смещение.
4. Проверил сохранённые заказы независимым запросом PostgreSQL с `created_at AT TIME ZONE 'Europe/Berlin'` и сравнил с фиксированными UTC+1 и UTC+2.

Например, оплаченный заказ `o_02357` создан `2026-03-29T22:40:08Z`. В Берлине это **30 марта, 00:40:08**, а фиксированное UTC+1 относило его к **29 марта, 23:40:08**.

На реальных данных после вебхуков сравнение суммы до скидок получилось таким (рубли):

| День | Правильно, Europe/Berlin | Фиксированное UTC+1 | Фиксированное UTC+2 |
|---|---:|---:|---:|
| 2026-03-27 | 24736 | 24736 | 31051 |
| 2026-03-28 | 58233 | 58233 | 48646 |
| 2026-03-29 | 34658 | 43964 | 45872 |
| 2026-03-30 | 59684 | 52201 | 59684 |
| 2026-03-31 | 35401 | 44064 | 35401 |

Это объясняет совпадение части дней и расхождение остальных. Какой именно участок ошибочен в исходной реализации, зависит ещё и от сезона запуска отчёта. В исправленной реализации результат одинаков зимой и летом.

Повторить диагностику после загрузки данных:

```bash
docker compose exec -T postgres psql -U postgres -d orders < scripts/diagnose-timezone.sql
```

## Как проверял результат

Работа выполнена с помощью ИИ-ассистента; выводы проверены тестами и запуском комплектного внешнего API, без подмены его реализации.

1. До изменений запустил исходные тесты на реальном PostgreSQL: **27/27 прошли**.
2. После изменений: **45/45 тестов прошли**, `npm run typecheck` прошёл. Существующие сценарии сохранены; точные ожидания daily-totals дополнены новыми полями.
3. Новые проверки покрывают смешанные старые/новые заказы, строковые суммы, фактическую оплату вместо процента, 100% скидку и нулевые дни; sync, обновление оплаты, повторные/устаревшие и конкурентные события; обогащение старых записей; невалидные оплаты; копейки и дробные копейки; границы диапазона в UTC+14 и UTC−12.
4. DST проверен для весеннего и осеннего перехода Берлина. Весенний отчёт проверяется с часами процесса и в январе, и в июле; ожидания одинаковые.
5. Загрузил приложенный `orders-mock-amd64.tar.gz`, запустил PostgreSQL, внешний API и приложение через `docker compose up -d --build`. До sync проверил рабочую БД: **0 заказов, 0 запусков sync**. Тесты используют отдельную БД `orders_test`.
6. Последовательно выполнил полный sync, отправку всех вебхуков и запрос отчёта. Ответ GET сохранён в `result.json` в корне проекта `orders-aggregator`.
7. `npm run verify-result` сравнил файл с независимой агрегацией PostgreSQL (`AT TIME ZONE`, SQL SUM): **совпали все поля всех пяти дней**. Проверка использует сохранённые заказы; это независимая проверка агрегации, а не повторная реализация всего внешнего API.

## Допущения и наблюдения

- Старый формат действительно встречается во внешнем API: у части заказов нет полей скидки. При **отсутствующем** `amountPaid` считаю `net = gross`; `null`, отрицательные, нечисловые суммы и оплата выше `amount` считаются невалидными. Один `discountPercent` не заменяет фактическую оплату.
- `NULL` в новой колонке означает неизвестную оплату старой версии, а не нулевую оплату. Поэтому миграция совместима с имеющимися заказами и не уничтожает данные.
- Чтобы повторный sync мог заполнить скидки уже импортированных заказов, допускается обогащение при том же `updatedAt`, только когда оплата ещё неизвестна и **все прежние поля совпадают**. После обогащения повтор становится `stale`. Старая версия не обогащает новую, а известная оплата при том же времени не заменяется. Это явно выделенное исключение из правила «только более новая версия».
- Сохранил исходную семантику отчёта: день определяется по `createdAt`, а не `updatedAt`; заказ `refunded` полностью исключается, частичные возвраты контрактом не описаны. Рубли в JSON — числа, без обязательных завершающих нулей.
- Во внешнем API встречаются строковые суммы. Обработка UTC-строк без суффикса зоны уже была в сервисе и сохранена. В исходном клиенте также уже предусмотрены 429, ошибка лимита внутри HTTP 200, ретраи и завершение пагинации пустой страницей с прежним курсором — эти механизмы не переписывал.
- Обнаруженную гонку версий устранил в БД; память одного экземпляра сервиса для такой гарантии недостаточна.

## Что доделал бы при наличии времени

- Согласовал бы с владельцами API обязательность `amountPaid`, правила дробных копеек, противоречивых полей и одинаковых времён версий. Добавил бы контрактные тесты HTTP-клиента.
- Для больших объёмов перенёс бы агрегацию в SQL и ограничил длину диапазона отчёта; добавил бы метрики невалидных заказов и причин ретраев.
- Для нескольких экземпляров приложения добавил бы распределённую блокировку sync и миграций, фоновое выполнение sync с возобновлением и обновление кэша таймзон.
- Подготовил бы отдельную сборку JavaScript с минимальными runtime-зависимостями и CI для проверок и контейнерной сборки.
